Prepare and publish releases from one form. Build Windows locally, watch macOS on GitHub, and verify the final release.

Vault Spend: sharded Windows draft

Select Windows: sharded draft in Build. Enter OneTrueAsian/vault-spend, the pushed release branch, a matching production version tag, and your token. Use release-windows.yml and tag input tag. Local profile fields are unused. Windows: serial draft is the fallback.

The tool pins the source commit, selects the gate explicitly, and tracks checks, shards, packaging and signing. Approve the protected signing job on GitHub. Completion verifies that the draft has the expected nonempty installers and signing companions; it does not independently verify their cryptography.

The release stays unpublished for owner review. macOS is not dispatched because its current workflow can publish the shared draft. Do not use the generic local publishing instructions below for this draft-first path. Reserved test versions v1.3.90 through v1.3.99 are refused.

Get started

Choose a repository and an application release profile. The profile defines its build system, version metadata, checks and exact artifacts.

  1. Install Windows, Python 3.10+ with Tkinter, PowerShell, Git and GitHub CLI, plus the tools required by your profile.
  2. Copy and configure profiles/custom-app.json. Its sample commands must be replaced with your application's commands. The Tauri profile is optional.
  3. Enter owner/repo, a stable vX.Y.Z tag and your token. Select the application clone, profile and Markdown release notes.
  4. Configure a macOS workflow only if your profile declares macOS assets.
  5. Click Build release to authorize preparation, checks, commits, merge/push, build and publication.

Each i icon provides field help. Read the detailed setup and profile reference.

Application configuration

Set the product name, default/release branches, required tools, JSON version properties, preparation/check/build command arrays, output directory and exact artifact names. Add generated metadata files to additional_release_files.

No Node, Rust, Tauri, Perl, E2E gate, changelog format or signing policy is required by a custom profile. Configure those only when your app needs them. Optional install_notes are supplied by the profile.

Set mac_assets to [] for local artifacts only. Otherwise a manual-only macOS publishing workflow must exist on the default branch and release source and publish the configured assets. Asset counts are configurable.

Release checklist

  1. Check repository access, clean tracked files and an unused tag.
  2. Prepare configured versions and application metadata.
  3. Run the configured release gates; a repeated failure stops the release.
  4. Commit configured files, merge into the configured default branch and push.
  5. Run the configured build and require fresh nonempty artifacts.
  6. Publish at the recorded commit SHA and monitor optional remote publishing.
  7. Verify the configured assets, stable release, tag commit and latest release.

GitHub token

Use a classic token with repo/workflow access or a fine-grained token with Contents and Actions read/write for the target repositories. Editing workflows may require Workflows write. The token is not saved or included in command arguments; activity logs redact it.

Form fields

Repository is owner/repo and must match the local Git origin. A blank release branch uses the profile template. The local folder is the application checkout. App profile selects its release recipe. Release notes are a nonempty Markdown file. Workflow settings apply only to selected remote builds. Hover each field's i icon for details.

Example

Repository: owner/app-repo
Tag: v1.0.1
Application folder: E:\Apps\app-repo
App profile: E:\ReleaseProfiles\my-app.json
Release notes: E:\ReleaseNotes\app-1.0.1.md

Configure your profile before use; the sample does not supply a build system.

Results and retries

Activity shows commands, errors and workflow links. Stop after step waits for the current command. Completed pushes and publication are retained. Stopping monitoring does not cancel GitHub jobs.

Local existing-tag mode adds configured local artifacts to an existing release while preserving the tag and unrelated assets. Replacing a different existing artifact requires an explicit profile option. Diagnose failed remote runs before retrying; code fixes may require a new tag.

Troubleshooting and limits

For failed checks, fix the app or profile. For missing artifacts, check the configured output paths and build command. For access errors, check repository/token/workflow access. Never retry new-release mode with an existing tag.

Local builds require Windows and stable vX.Y.Z tags. Optional remote publishing is exposed as a macOS workflow. This tool publishes GitHub releases; it does not provision applications or deploy web/cloud services.

GitHub-only modes use your workflow's own gates. The legacy Windows recovery mode requires a compatible recovery workflow; that contract is not required for normal releases.
