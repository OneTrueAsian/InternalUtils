GitHub Release Tool

Create a release tag and start Windows and macOS build workflows from one form. Your GitHub workflows build the app and publish its release files.

Get started

Use Windows with Python 3.10 or newer, Tkinter, and Windows PowerShell 5.1 or PowerShell 7. Tkinter comes with the standard Windows Python installer. No pip packages are required.

  1. Keep all files in the release-tool folder together.
  2. Double-click ReleaseTool.pyw, or run the command below from the InternalUtils repository.
  3. Enter the repository, branch, tag, and API token. Check the two workflow filenames.
  4. Click Start release builds. Follow the run links to check build progress.
python .\release-tool\ReleaseTool.pyw

Hover over an i icon beside a field for a quick explanation. You can also focus or click the icon. Press Escape to dismiss its instructions.

Prepare the app repository

The tool works with other apps by changing the repository and workflow filenames. Each app needs its own Windows and macOS release workflows.

  • Store the workflow files in the app repository, under .github/workflows/. For example, .github/workflows/release-windows.yml and .github/workflows/build-macos.yml.
  • Commit and push both workflow files to the repository's default branch and to the branch you want to release.
  • Enable GitHub Actions and the two workflows. Each workflow must declare workflow_dispatch: in block YAML format.
  • Both workflows must accept the same tag input name, or both must accept no inputs and use the dispatched Git ref.
  • The workflows must build the tag and create or update its GitHub Release. Their settings control test gates, packaging, signing, draft releases and prereleases.
  • Commit and push the app's version changes and release code before using this tool.
The tool currently requires both Windows and macOS workflows. It does not install workflows, bump app versions, commit files or push local changes.

Workflow setup reference: GitHub: manually running a workflow.

Create your GitHub API token

  1. Open GitHub Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Select the resource owner that owns the app repository. Set an expiration.
  3. Select the repositories you plan to release. All repositories supports other current and future repositories owned by the selected owner.
  4. Under Repository permissions, choose Add permissions and add the permissions below. Clear any search text first, then search for each permission by name.
  5. Generate the token and enter it in the tool's GitHub API token field.
PermissionAccessPurpose
ActionsRead and writeCheck workflows and runs, then request builds.
ContentsRead and writeRead the remote branch and workflow files, and create the release tag.
WorkflowsRead and writeGitHub may require this when creating references involving workflow files.
MetadataRead-onlyIncluded automatically.

A classic token uses repo, with workflow where required. Organization access may require owner approval or SSO authorization. A fine-grained token is scoped to its selected resource owner.

The field is masked and cleared when starting. The token travels to PowerShell over a private input pipe; it is not saved to disk or placed in command-line arguments. Logs redact the supplied token. It exists briefly in process memory.

Fill out the form

FieldWhat to enter
RepositoryThe app's owner/repo, such as OneTrueAsian/vault-spend. Choose the app repo, not InternalUtils.
Remote branchThe pushed branch containing the code you want to release. Use release-1.3.0 for that release branch, or main when main contains your intended release code. Blank uses the repository's default branch.
Release tagA Git tag such as v1.3.0. A new tag points to the chosen branch's latest remote commit. Set the app's version in the source before releasing.
GitHub API tokenYour personal access token for the app repository, with the permissions above.
Windows workflowThe filename only, such as release-windows.yml. Do not include .github/workflows/.
macOS workflowThe filename only, such as build-macos.yml. Use a workflow that publishes a release; build-macos-check.yml only validates builds.
Tag input nameUsually tag. It must match the input accepted by both workflows. Leave blank if both workflows accept no inputs and use the dispatched Git ref. The dispatched ref is always the release tag.

Example: release Vault Spend 1.3.0

Assuming your app version, release code and both workflow files are committed and pushed:

Repository:        OneTrueAsian/vault-spend
Remote branch:     release-1.3.0
Release tag:       v1.3.0
GitHub API token:  [your token]
Windows workflow:  release-windows.yml
macOS workflow:    build-macos.yml
Tag input name:    tag

Click Start release builds. The tool checks the branch and workflows, creates or verifies v1.3.0, then requests both builds against that tag.

Understand results and retries

  • Builds requested means the workflow requests succeeded. It does not mean builds or publication finished.
  • Use the clickable build links or Open GitHub Actions to inspect build progress and failures.
  • Open release opens the tag's release page. It may be absent until a workflow publishes it.
  • The UI log shows request failures and partial success. Logs currently remain in the UI and are not saved to disk.
  • If one request fails, the other is still attempted. The tag is retained. Enter your token again to retry with the same tag and its original branch commit.
  • An existing tag can be reused only at the same commit. The tool never moves or deletes tags.
  • Existing queued, running or successful runs for the same tag and commit are reused when found. Failed or cancelled runs can be requested again.
Automatic tag triggers are checked before dispatch, but delayed events or simultaneous clients can still create duplicates. For predictable manual orchestration, use workflow_dispatch only in your release workflows.

Troubleshooting

GitHub rejected the token / HTTP 401

Check the token value and expiration. Generate a replacement if it expired, then enter it again.

GitHub denied access / HTTP 403

Check the token's repository permissions, selected owner and repository access. Organization approval, SSO authorization or a rate limit may also prevent requests.

Repository, branch or workflow not found / HTTP 404

Verify owner/repo, the remote branch name and workflow filenames. Push missing files to both branches. GitHub can also return 404 when the token lacks access to a private repo.

Workflow is disabled or lacks manual dispatch

Enable it in GitHub Actions and add a block-format workflow_dispatch: trigger. Make sure it exists on the default and selected branches.

GitHub rejected a request / HTTP 422

Check the Git tag and the workflows' input names. Both workflows must accept the tag input you selected. If the tag was created but dispatch failed, it remains available for retry.

Tag points to a different commit

The branch may have advanced since the tag was created. Use a new tag for the new commit, or select a remote branch still pointing to the original tagged commit. You can rerun an existing failed build directly in GitHub Actions.

The request succeeded, but the build failed

Open the failed run in GitHub Actions and inspect its job logs. Build dependencies, test failures, signing secrets and packaging are controlled by the app's workflows.

The UI does not launch

Run python .\release-tool\ReleaseTool.pyw from a terminal to see startup errors. Check that Python includes Tkinter and that all tool files are together. PowerShell must also be available.
