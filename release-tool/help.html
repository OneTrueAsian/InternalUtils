Get started

The default Local: full release mode builds Windows on your computer and uses GitHub Actions for macOS. Keep all tool files together and launch ReleaseTool.pyw. Python 3.10+, Tkinter and PowerShell are required.

  1. Enter the app repository, new tag and token under Release details.
  2. Under Local release, choose the local app clone, JSON app profile and Markdown release notes.
  3. Under Workflow settings, check the macOS release filename and tag input.
  4. Click Build release to run the whole pipeline, including commits, merge/push and publication.

Hover or activate each i icon for field instructions. Focus alone does not open help.

Local build prerequisites

Install Git, GitHub CLI, Node/npm, Rust and Visual Studio C++ build tools. The app needs the Tauri CLI dependency and WebView2 runtime. For vendored OpenSSL, install Strawberry Perl and use short repository/target paths. The Vault Spend profile prefers Strawberry Perl, runs builds through PowerShell and preserves the local Cargo cache.

Use profiles/tauri-vault-spend.json for Vault Spend or customize profiles/tauri-generic.json for another Tauri app. Profiles contain command argument arrays, exact installer names and app-specific metadata settings. Review commands before running a profile. They do not contain tokens.

The macOS workflow must be registered on the default branch and support manual-only workflow_dispatch on the release source. Local Windows mode does not use the Windows workflow.

Full release pipeline

  1. Verify origin matches the selected repository, the tracked working tree is clean, the new tag is absent, and show changes since the previous release.
  2. Bump the three version files, regenerate both locks, update the in-app notes and release metadata.
  3. Run type check, lint, unit tests, Rust format/clippy checks and Rust tests. A failure is repeated once alone, then stops the release.
  4. Commit Release X.Y.Z, merge into the default branch with a merge commit, and push. Incoming merge changes are checked again when they alter the tested tree.
  5. Build Windows locally with npx tauri build. Require fresh, nonempty NSIS and MSI installers with the exact product/version filenames.
  6. Create the stable release and tag at the recorded merge SHA, then start and watch macOS.
  7. Verify four expected nonempty assets, stable publication, the tag commit and releases/latest.
No E2E commands are added by default, following your documented process. Configure an app's extra gates in its profile. Publication happens after Windows succeeds; if macOS fails, Windows assets remain available.

Token and privacy

A classic token needs repo and workflow. Fine-grained tokens need target-repository Contents and Actions read/write, plus Workflows permission where required. Local GitHub CLI and its scoped Git credential helper receive the token through their environment. Build commands do not receive it. GitHub-only dispatch uses stdin. No token is saved to disk or put in command arguments, and logs redact it.

Form fields

FieldWhat to enter
BuildLocal: full release for a new release; Local: Windows existing tag to add Windows installers to an existing release. GitHub-only alternatives retain their workflow gates.
RepositoryThe app's owner/repo; its local origin must match.
Release branchBlank uses the profile's release-X.Y.Z pattern. It must differ from the default branch. Existing-tag local mode does not use this field.
Release tagA stable tag such as v1.0.1. Full mode rejects existing tags; existing-tag mode preserves the original commit.
Application folderThe local application clone, not InternalUtils. Commit code changes before starting.
App profileA JSON release recipe with check commands, versions/locks, metadata and exact asset patterns.
Release notesA Markdown file outside the app repository. Bullets under What's new / Fixes and improvements become the in-app notes. Unsigned install notes are appended if missing. Not used for existing-tag mode.
macOS workflow / tag inputThe publishing filename, usually build-macos.yml, and its tag input, usually tag. Windows workflow is unused locally.

Example: new local release

Build:             Local: full release
Repository:        owner/app-repo
Release branch:    release-1.0.1 (or blank)
Release tag:       v1.0.1
Application folder: E:\Apps\app-repo
App profile:       profiles/tauri-generic.json
Release notes:     E:\ReleaseNotes\app-1.0.1.md
macOS workflow:    build-macos.yml

My App 1.0.1 makes account setup easier.

- **Account setup.** Clearer instructions help you create an account.

## Fixes and improvements

- Fixed the saved account name disappearing after a restart.

Existing-tag Windows and recovery

Local: Windows existing tag checks out the original tag temporarily, runs configured checks and builds/uploads Windows installers. It restores the original checkout and preserves macOS assets, release notes and the tag. An existing published stable release page is required. Different existing Windows assets are not overwritten unless replace_windows_assets is explicitly enabled in the profile.

Stop after step waits for the current local command, then stops before the next. It does not undo pushed commits or published files. During macOS monitoring, polling stops but GitHub builds continue. Copy log captures the redacted activity output.

If macOS failed temporarily, open its run and rerun failed jobs, or use gh run rerun RUN_ID --repo owner/app-repo --failed. Do not rerun the full new-release pipeline against an existing tag. Use the documented recovery commands for intentional asset deletion or release withdrawal; the tool never withdraws automatically.

Troubleshooting

  • Tracked changes: fix or commit them on the release branch. Prepared versions can resume before tag creation when notes and candidate metadata agree.
  • Check fails twice: stop and fix the cause; the tool never skips the gate.
  • Perl / long path: install Strawberry Perl, configure its path and shorten the repository/target directory.
  • Missing/stale installer: inspect the Windows build output. Exact fresh versioned filenames are required.
  • Tag already exists: use local Windows existing-tag mode. Tags are not moved or deleted.
  • 403/404: verify token access, repository owner and workflow registration.
  • Partial release: retain the successful assets and fix the failed platform; an incomplete release is not counted as success.
  • Repository lock: if the owning process crashed, confirm it exited before removing .git/internalutils-release.lock.

The original Windows + macOS and Windows only · existing tag options use GitHub workflows. They retain the workflow's desktop E2E gate and may take longer. Remote recovery uses a workflow branch and requires recovery/source_sha inputs and Recover Windows run naming.

Other repositories and apps

Choose a profile for the target checkout: tauri-generic.json for Tauri apps, custom-app.json for other build systems, or tauri-vault-spend.json for Vault Spend. Copy and edit the profile before use.

Custom profiles configure product name, default/release branches, JSON version properties, required tools, preparation/check/build commands, target directory and exact asset names. Commands are argument arrays; {version} and {tag} are substituted. List any generated release files in additional_release_files so they can be committed.

Set mac_assets to [] for Windows-only apps; macOS fields are ignored. Otherwise provide a manual macOS publishing workflow and its expected asset names. Asset counts are configurable. Stable vX.Y.Z tags are required. Your application must already have its own working build scripts and tests.

See the README section “Using another repository or application” for JSON examples and setup details. Use trusted profiles: their commands run locally and starting a release authorizes commits, pushes and publication.
